# Reality check — 2026-W39 (21 Sep 2026)

Compares what the org's documents and pipelines claim against what is
actually true, right now. Read-only — nothing here was fixed, only checked
and, per the standing rule, filed to `docs/ops/queue.md` as tickets. Ordered
by consequence: money and user-visible things first. Every finding says how
it was verified.

**Headline: this is the third week running that every weekly strategy output
reached a real, working state and then never left its own branch — including
last week's edition of this exact job.** That is not a new kind of failure;
it is proof the failure is structural, not incidental (§6). Underneath it,
~6,600 lines of tested product code (two broker integrations, a real P/L
accuracy fix, migrations) have been sitting in one open, unmerged PR for a
week (§2), a Saturday deadline tied to the weekly digest passed with nobody
confirming it (§2), and a security-adjacent secret has been wrong for nine
days (§2). The blog was fully down for six days and, as far as CI evidence
shows, came back today (§1). None of this reached the owner: `main`'s own
queue is telling him a stale, disproven story (§4), and the channel this job
is supposed to email through is still dead (§0, §8).

## 1. The blog: six days down, apparently fixed today — verified against CI, not the live page

**Claim (`content/PLAN.md`):** one article every day; the Published table
shows entries through `option-assignment-what-happens` (foundations·10,
2026-09-21).

**Reality, reconstructed from `content-merge.yml`'s run history (45 runs)
and its own commit-log comments, which this report checked rather than took
on faith:**

- **15–20 Sep: the pipeline was down for six consecutive days.** Runs
  #32–#44 against the one article being written that week (gamma,
  foundations·9) are **13 straight `failure` conclusions** on GitHub Actions
  (verified via `mcp__github__actions_list`, workflow `content-merge.yml`).
  Root cause, in two layers, both readable in `content-merge.yml`'s own
  inline history: the merge gate diffed each branch against `staging`
  instead of the branch's actual fork point, so it blamed a 6-file post for
  73 commits of trunk divergence and refused it every time; separately, the
  destination was `staging`, which sessions branching from `main` can't see,
  so the same article was drafted from scratch **four times** (16, 18, 19,
  20 Sep) by different sessions each finding no prior draft.
- **This is corroborated independently**, not just by the workflow's own
  comments: the board pack for that exact week (`docs/board/2026-W38.md`,
  stranded on `claude/gifted-feynman-njvd5k`, §6) says the same thing from
  the outside — "a second post (gamma) was independently drafted, reviewed
  and cleared **twice** by two different sessions three days apart, with
  neither reaching `staging` or `main`" — and quotes the owner directly:
  *"As always, the blog is not posting anything for days. And you keep
  saying it's fixed!!!!"* This is the fourth distinct root cause of "no blog
  posts" since 3 Sep (allowlist too narrow → same, wider → a second file
  type tripped it → PostgREST batch-shape bug → this week's wrong diff
  base), each one fixed for real and each one hiding the next.
- **Today, 21 Sep, the pipeline ran clean for the first time under a
  redesigned workflow** (renamed `content-merge.yml`'s display name from
  "Merge content to staging for review" to "Merge and publish content";
  destination changed to `main`, fork point fixed). Run #45
  (`35594343792`, 11:29:43–11:29:56 UTC) is green end-to-end: gate passed,
  merge into `main` succeeded, and it dispatched `publish-blog.yml`, which
  **itself ran and succeeded** (run #12, `35594358256`, 11:29:54–11:30:10
  UTC) — a genuinely separate CI job that authenticates to
  `https://yecfbeohyakuoyczvdbj.supabase.co` (production, verified by
  reading `publish-blog.yml`'s `SUPABASE_URL` line) with
  `SUPABASE_SERVICE_ROLE_KEY` and writes the post. **This is the strongest
  evidence available from this session that a real write reached production
  today** — it is not the same as fetching `/blog` and seeing the article,
  which this session cannot do (§0).
- **The bypass.** `gamma-options-meaning.md` reached `main` yesterday (20
  Sep, `c4b0a57`, 11:19:18 UTC) as a **single-parent commit authored
  directly on `main`**, not through the gate at all — at the same minute
  the gate's own run for that exact commit message was independently
  failing on a `claude/*` branch. Someone or something pushed straight past
  the checkpoint to get the article out; `publish-blog.yml` run #11 the same
  day (13:29:38 UTC, triggered by a plain push, not a dispatch) confirms it
  then published. Whether that direct push was a deliberate manual override
  or a second, undocumented path is not determinable from the commit alone.
- **`content/blog/` on `main` now holds 13 files**, all reflected in
  `content/PLAN.md`'s Published table with real review-chain notes
  (desk-editor, seo-editor, compliance-gate) for each. No orphan file (blog
  post in the repo with no PLAN.md row) and no phantom PLAN.md row (entry
  with no file) — checked directly, `ls content/blog/` against the table.

**Who fixes it / what's left:** nothing — this one fixed itself today,
verify by watching tomorrow's run rather than re-litigating. The open
question is whether the live `/blog` and `blog_posts` actually reflect this

  header hasn't been keeping pages out of Google.** `worker/index.js:40`
  sets `X-Robots-Tag: noindex, nofollow` unconditionally — verified by

  names only Alpaca (`"Connect your Alpaca account now — free"`); no mention
