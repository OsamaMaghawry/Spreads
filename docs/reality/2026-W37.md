## 1. The blog: a fourth post is finished and stuck — same failure, new instance

**Claim (`content/PLAN.md`):** "The blog now publishes **one article every
day**... committed; merged and published automatically when the diff is
content-only." Its own Published table lists three live posts, most recent
2026-09-02 (`credit-spread-max-loss`).

**Reality:**

- `content/blog/` on `main` holds exactly those **three** files. No post has
  reached `main` since 2 Sep — **five days** with no new post landing, against
  a daily-publication claim. (2026-09-05/06 are a weekend; PLAN.md does not
  say weekends are skipped, so if that's the intent it isn't written down.)
- A **fourth post was written today**: `what-is-an-options-contract.md`
  (foundations #1), fully drafted, seo-editor and desk-editor passes applied,
  compliance-gate shipped with no findings (commit `ba6d998`, 11:30 UTC,
  branch `claude/compassionate-edison-08f1ie`). It is **not on `main`**, and
  `content/PLAN.md`'s Published table on `main` says nothing about it —
  the file that should record this doesn't know it happened.
- **Root cause, found by reading the automation itself
  (`.github/workflows/content-merge.yml`):** the auto-merge gate only
  accepts a push where every changed file matches `content/blog/**`,
  `content/PLAN.md`, or `docs/seo/**`. Today's post's diff against `main`
  (`git diff origin/main...origin/claude/compassionate-edison-08f1ie
  --name-only`) also touches
  `landing/public/assets/blog/contract-bought-vs-sold.svg` and
  `landing/public/assets/blog/options-contract-fixed-fields.svg` — the two
  diagrams the commit message says the post ships with. Those paths are
  outside the gate's allowlist, so it correctly judges the push "not
  content-only" and leaves it "for a person to merge" — and no person has.
- **This is not a one-off miss: the automation has never once fired
  successfully.** `git log --all --author="deltamint-content"` and
  `--grep="^Publish: "` — the bot identity and commit-message format the
  workflow itself uses when it merges — return **zero commits, on any
  branch, ever.** Every post that has reached `main` (three of them) got
  there some other way (a manual/human merge or a squash commit), never
  through the pipeline `content/PLAN.md` describes as the mechanism.
- Even a successful merge would not guarantee a live post: `publish-blog.yml`
  refuses to run without `SUPABASE_SERVICE_ROLE_KEY`, which
  `docs/ops/queue.md`'s oldest open ticket (2026-09-02, still open today)
  says is not set as a GitHub secret.
- **Whether the three posts already on `main` are actually live and rendering
  at `deltamint.app/blog` cannot be checked** — §0.

**Who fixes it:** the content-merge gate's allowlist needs
`landing/public/assets/blog/**` (or wherever post diagrams live) added, or
illustrated posts will keep stalling silently forever — systems-engineer or
whoever owns `.github/workflows/`. Separately, the owner needs to set
`SUPABASE_SERVICE_ROLE_KEY` (already queued) before a merge means anything.

**Verified by:** `ls content/blog/` on `main`; `git log --all` for the bot
identity and commit format; reading `content-merge.yml` and
`publish-blog.yml`; `git diff` of the stuck branch against `main`.
**Not verified:** live `/blog`, live `blog_posts` rows — blocked, §0.

the product's actual behavior. `docs/ops/queue.md`'s Stripe ticket
(2026-09-02, still open) — set the product/prices/webhook secrets — is also
unresolved, consistent with billing being built but not switched on.

**Who fixes it:** vp-product — `pricing.md` §1 needs a one-line correction
