# Branding consistency audit — 2026-W36

Cadence: biweekly, even ISO week → normally a light "what changed since last
audit" pass. No prior audit exists in `docs/branding/` on any branch, so
there is nothing to diff against — this run does the full sweep instead, and
becomes the baseline future light weeks compare against.

Scope walked: the app (`src/`), the landing site (`landing/`), the blog
(`content/blog/`), auth + alert/digest emails (`supabase/auth/`,
`supabase/functions/`), the exported PDF
(`src/components/analysis/ExportPdfButton.jsx`). Live-site check
(`deltamint.app`, `dashboard.deltamint.app`) via WebFetch returned
`EGRESS_BLOCKED` from this environment — not verified against the deployed
site this cycle, source only. (Separately: this contradicts
`docs/context/reachable.md`'s 2026-08-31 row claiming both domains are
`✅ 200`, while the staging `docs/ops/queue.md` logs "403 at CONNECT since 31
Aug" for the same domains. Not a branding finding — flagging for whoever
owns `reachable.md` to reconcile.)

Truth of claims is desk-editor's question; disclosure sufficiency is
compliance-gate's. Neither is judged here — flagged and handed off where it
came up.

## This cycle's asks (top five, ranked by exposure)

**1. Two parallel design systems — the trading app mostly ignores the `dm`
palette; only Admin and auth chrome use it.**
Surfaces: the whole app. Every trader-facing screen (`Dashboard.jsx`,
`Screener.jsx`, `Accounts.jsx`, `AccountDetail.jsx`, `AccountHistory.jsx`,
`AccountAnalysis.jsx`, open/close dialogs) is built on generic Tailwind
`slate-900`/`slate-500` text and `emerald`/`rose`/`amber`/`sky`/`violet`
color, never `dm-text`/`dm-sub`/`dm-accent`. `dm-accent` (`#534AB7`, brand.md's
"primary actions") appears only in `Admin.jsx`, `src/components/admin/*.jsx`,
`AuthLayout.jsx`, and the `Layout.jsx` nav — i.e. the surface almost nobody
but the founder sees is on-brand, and the one every paying trader lives in
is not. The "primary CTA" color changes with no logic tied to money vs. not:
emerald ("Scan {n} tickers" `Screener.jsx:100`, "Connect Alpaca" submit
`AccountForm.jsx:120`, "Export PDF" `ExportPdfButton.jsx:161`, close-position
confirm `ConfirmSubmit.jsx:16`) vs. `dm-accent` purple (Admin only) vs.
shadcn's default near-black (`--primary: 0 0% 9%`, `src/index.css:15`) on
Login/Register (`Login.jsx:95`). Three different "this is the button that
matters" colors on one login → screen → trade path.
**Fix:** repoint the app's primary-action styling (buttons, focus rings,
active nav) at `dm-accent`; retire the ad hoc emerald/near-black buttons. A
shared button-class/Tailwind-config change, not a copy or feature change.

**2. The `Layout.jsx`/H1/pricing-page three-way name split for the
Positions Monitor — the open queue ticket, confirmed and wider than filed.**
Surfaces: app nav (every page), the pricing page. Nav label reads
`"dashboard"` (`src/components/Layout.jsx:15`); the page's own H1 reads
`"Positions Monitor"` (`src/pages/Dashboard.jsx:41`, brand.md's canonical
name); the pricing page's feature bullet reads `"Position monitor with live
P/L"` — singular, lowercase (`landing/public/pricing/index.html:68`). A
prospect reads "Position monitor" on pricing, clicks through, sees a nav
item called "dashboard," and lands on a page whose own heading says
"Positions Monitor." All three should read "Positions Monitor."
**Fix:** change `Layout.jsx:15` nav label to `"Positions Monitor"` (matching
the other nav items' casing) and `landing/public/pricing/index.html:68`
bullet to `"Positions Monitor with live P/L"`.

**3. The Analysis feature carries three names inside one user action —
including on the PDF that leaves the product.**
Surfaces: the Analysis page, its exported PDF. On-screen H1 reads
`"Analysis"` (`src/pages/AccountAnalysis.jsx:124`, matches brand.md exactly).
The same render passes `title={... "Performance Analysis"}` into the PDF
export (`AccountAnalysis.jsx:147`) — brand.md's own table lists "performance
page" as a forbidden synonym. The exported PDF footer then reads
`"DeltaMint — economic performance report. Not a tax document and not
investment advice."` (`ExportPdfButton.jsx:107`), and that same phrase
already appears on-screen before export
(`AccountAnalysis.jsx:192`). Highest-stakes instance: per the component's
own comment the PDF is "the one artifact that leaves the product" — what
gets forwarded to an accountant or a spouse, permanently, outside the app's
control.
**Fix:** change `AccountAnalysis.jsx:147` title prop to
`` `${name} — Analysis` `` and the "economic performance report" strings
(`AccountAnalysis.jsx:192`, `ExportPdfButton.jsx:107`) to "Analysis."
**Hand-off:** whether "economic performance report" was chosen deliberately
to avoid an investment-performance claim, rather than by accident, is a
desk-editor/compliance-gate call before the wording is simply replaced —
flagging the inconsistency here, not the choice of replacement word.

**4. Red means "loss/risk" per brand.md, and renders as at least five
different colors for that one meaning.**
Surfaces: app-wide P/L, landing hero, exported PDF, generic form errors.
brand.md fixes `dm-negative` (`#993C1D`, rust) as "Losses and risk — and
nothing else," but it's used at exactly one call site
(`src/pages/OAuthCallback.jsx:109`). Everywhere else loss/negative P/L uses
Tailwind `rose-600`/`rose-700` (60 call sites, e.g.
`TradeHistoryTable.jsx:25`, `CloseDialog.jsx:228`) — a bright pink-red, a
different color family from the rust-brown `dm-negative`. The landing page
defines its own `--rose` token (`#B4485C`/`#E68094`,
`landing/public/assets/site.css:20,42`) for the same "loss" meaning. The
PDF's "PAPER TRADING" banner is hardcoded `rgb(180, 72, 92)`
(`ExportPdfButton.jsx:81`) — literally `#B4485C`, matching the landing rose,
not the app's rose-600 and not `dm-negative`. Shadcn's
`--destructive: 0 84.2% 60.2%` (`src/index.css:23`, ≈`#ef4444`) is a fifth
red, used for generic form errors (`Login.jsx:51`). Same pattern on warning:
`dm-warning` (`#854F0B`, `src/index.css:52`) is defined but used nowhere —
every real warning uses Tailwind `amber-*` instead
(`Screener.jsx:107,109`, `PriceControl.jsx:151,157`,
`EarningsWarning.jsx:20`), and the landing page has a third `--amber`.
**Fix — answers brand.md's own "(proposed)" question:** collapse to the `dm`
scale everywhere: replace `rose-*`/`amber-*` usages that mean loss/risk/
warning with `dm-negative`/`dm-warning` across the app, the landing site,
and the PDF banner color, so red means one thing and is one hex everywhere.

**5. Green is also used decoratively, which brand.md's own proposed rule
already calls a defect.**
Surfaces: app-wide. The same emerald that means "gain" in P/L cells
(`text-emerald-600`, e.g. `TradeHistoryTable.jsx:25`) is, on the same
screens, also the color of the scan progress bar (`Screener.jsx:124`), the
"connected" status dot (`AccountSection.jsx:126`), a preset chip with no P/L
meaning (`ScanPresets.jsx:99`), and every primary button in item 1. On
`CloseDialog.jsx`, a semantic emerald P/L figure (line 228) sits next to a
decorative emerald "reset" button (line 343) — the same color, two meanings,
four pixels apart.
**Fix:** same remedy as items 1/4 — reserve mint/emerald green for P/L and
connection-state truth only; move decorative "primary action" and
"in-progress" green to `dm-accent` or a neutral.

## Rest of the list (ranked, waiting — not this cycle's asks)

6. **Tone break in a loading state.** `AccountAnalysis.jsx:111` reads
   `"Crunching performance…"` while every other loading state in the app is
   a flat `"Loading…"` (`Admin.jsx:85`, `Accounts.jsx:202`) — the one
   playful string against an otherwise flat register. Fix: change to
   `"Loading…"`.
7. **Emoji as severity indicators in transactional email**, duplicated in two
   places. `supabase/functions/_shared/watchReport.ts:83` (`dot()`) and
   `supabase/functions/positionWatch/index.ts:193` (`sev()`) both render
   🔴/🟠/⚪ in the daily digest and real-time alert emails — independently
   implemented rather than shared. brand.md only bans emoji "in headings"
   (line 38), so this isn't a clean violation as written, but no other
   audited surface uses emoji anywhere. Brand-book gap, proposed below.
8. **`sky`/`violet`/`amber` used for lifecycle-status chips with no
   documented meaning.** `TradeHistoryTable.jsx:14-16`: `closed`=sky,
   `assigned`=amber, `exercised`=violet — a status vocabulary brand.md
   doesn't address. Low exposure (one table). Brand-book gap, proposed
   below.
9. **Landing page runs its own palette, unified only at the accent.**
   `landing/public/assets/site.css:9-26` defines its own
   `--paper`/`--surface`/`--ink`/`--mint`/`--rose`/`--amber` (light+dark).
   `--brand: #534AB7` matches `dm-accent` exactly; `--mint`/`--rose`/`--amber`
   don't match `dm-mint`/`dm-negative`/`dm-warning` (see item 4). Lower
   priority than the app-side collapse since this is a shipped, working
   dark/light design — but the derivation rule should be recorded so the
   next redesign doesn't drift further. Brand-book gap, proposed below.
10. **Auth/alert email colors don't match `dm-text`/`dm-sub`/`dm-accent`.**
    `supabase/auth/confirm-signup.html:18` uses `#4f46e5` (Tailwind
    indigo-600, not `dm-accent` `#534AB7`) and generic slate text hexes;
    `watchReport.ts` and `positionWatch/index.ts` alert emails use the same
    slate hexes, consistent with each other but not with `dm-text`
    (`#201B3A`)/`dm-sub` (`#6A6294`). Every signup sees the confirm-signup
    one. Fix: swap the hardcoded hexes for the `dm` equivalents in all three
    templates.
11. **PDF header text is generic slate, not `dm-text`.**
    `ExportPdfButton.jsx:92` renders `rgb(15,23,42)` (Tailwind slate-900)
    rather than `dm-text` (`#201B3A`). Cosmetic, lowest priority.
12. **`dashboard.deltamint.app` as the literal subdomain.** Infrastructure,
    not copy — a domain rename is rebrand-scale and out of this brief's
    scope. Noted only so it isn't mistaken for an unaddressed instance of
    the items 2/6 naming violation.

## Proposed rules for `brand.md` (silent today; vp-product to accept)

- *"No emoji anywhere in product surfaces, including transactional email;
  severity is conveyed by the `dm` semantic colors and words
  (critical/warning/info), not by color-coded emoji."* (closes item 7 — also
  de-duplicate `dot()`/`sev()` into `_shared` once a rule exists to enforce.)
- *"Lifecycle/status chips (closed, assigned, exercised, etc.) use a single
  neutral chip style with text, not a rainbow of Tailwind hues — reserve
  color for money and risk only."* (closes item 8)
- *"Any surface that defines its own color tokens (landing, email, PDF)
  derives them from the `dm` hexes, not from Tailwind defaults or invented
  values."* (closes item 9, and is really the general form of the item 4
  fix)
- Resolves brand.md's own open question (line 28-31): red/green are
  semantic only; the app's Tailwind emerald/rose/amber/sky/violet usage
  does **not** get sanctioned as-is — it collapses into the `dm` scale (item
  4/5), except lifecycle-status hues, which get their own neutral treatment
  per the rule above rather than either meaning.
