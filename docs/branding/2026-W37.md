# Branding consistency audit — 2026-W37

Cadence: biweekly, odd ISO week → full consistency audit. `docs/branding/
2026-W36.md` was itself a full sweep (no baseline existed before it), so this
is the first genuine "compare against last audit" cycle.

Scope walked: the app (`src/`), the landing site including the homepage and
the pricing page separately (`landing/public/index.html`,
`landing/public/pricing/index.html`, `landing/public/assets/site.css`), the
blog content (`content/blog/`) and its hub/rendering layer
(`landing/src/blog.js`, `landing/src/render.js` — the blog has no static
files under `landing/public/blog/`; it's served entirely by the Worker from
`blog_posts` rows, so the code that shapes every hub/post/RSS page was read
instead), auth email (`supabase/auth/confirm-signup.html`) and the
alert/digest edge functions (`supabase/functions/_shared/watchReport.ts`,
`supabase/functions/positionWatch/index.ts`), and the exported PDF
(`src/components/analysis/ExportPdfButton.jsx`, called from
`src/pages/AccountAnalysis.jsx`).

Live-site check: `WebFetch` on `https://deltamint.app` returned
`EGRESS_BLOCKED`. This matches the existing `docs/context/reachable.md` row
(`dashboard.deltamint.app / deltamint.app — ❌ 403 (policy, at CONNECT) —
2026-09-04`), so not re-recorded as a new blocker — the register already has
it, current as of today. Not verified against the deployed site this cycle
either; source only, same as W36.

Truth of claims is desk-editor's question; disclosure sufficiency is
compliance-gate's. Neither is judged here — flagged and handed off where it
came up.

## This cycle's asks (top five, ranked by exposure)

**1. Landing homepage hero and meta/social copy call the product's core
feature "a scanner," while the app, the pricing page, and the homepage's own
mockup section three lines later all call it "Screener"/"Market Screener."**
Surfaces: `deltamint.app` homepage (the highest-traffic surface that
exists — every visitor, every search snippet, every social share), the app,
the pricing page.
Exact text: `landing/public/index.html:7` (`<meta name="description">`),
`:18` (`og:description`), `:24` (`twitter:description`), and `:136` — the
visible dek under the H1 — all read *"A scanner that finds trades based on
your rules…"* Meanwhile the same file's own animated mockup, 224 lines
further down, carries `<div class="eyebrow">Screener</div>` (`:360`) and
`<h1>…Market Screener</h1>` (`:370`, `:432`), matching the app's own
`src/pages/Screener.jsx:93` H1 exactly (`Market Screener`). brand.md's own
table (line 52) already names this as a known drift to sweep: *"'Scanner'
appears in some copy where 'Screener' is meant."* This is that instance, and
it's not a buried string — it's the meta description Google indexes and the
sentence under the H1 every visitor reads first.
**Fix:** replace "scanner" with "Screener" in
`landing/public/index.html:7,18,24,136`.

**2. The Positions Monitor name split, resolved on one side, still broken on
the other — plus "Screener" vs. "Market Screener" is its own live split, not
yet in brand.md.**
Surfaces: app nav (every page, every session), the app's own Screener page,
the pricing page, the homepage mockup.
Exact text: `Layout.jsx:19` nav label is `"positions"` (lowercase, generic
word — the 2 Sep fix that closed the *old* ticket). `Dashboard.jsx:58` H1 is
`"Positions Monitor"` (canonical, correct). `pricing/index.html:125,165`
now correctly says `"Positions Monitor"`. So on this leg, nav is the one
surface out of step with everything else, including its own page's H1 one
click away. Separately: brand.md's canonical table (line 53) says the
feature is called **"Screener,"** full stop, not "Market Screener," yet
`Screener.jsx:93`, `landing/public/index.html:370`, and `:432` all say
**"Market Screener."** Two different splits, same feature area.
**Fix:** change `Layout.jsx:19` nav label from `"positions"` to `"Positions
Monitor"` (or, if nav space genuinely can't hold two words, that's a
brand.md exception to propose explicitly, not a silent shortening);
separately, drop "Market" from `Screener.jsx:93`,
`landing/public/index.html:370,432` so all three read "Screener," matching
the canonical table and the pricing/nav copy.

**3. Red renders as at least five different hex values for one meaning
("loss/risk"), and the exported PDF — the one artifact that leaves the
product permanently — carries a color that matches none of the app's.**
Surfaces: app-wide P/L (83 `rose-*` call sites across 38 files), the
exported PDF, the landing homepage, generic form errors.
Exact values: `dm-negative` `#993C1D` (brand.md canonical, one call site:
`OAuthCallback.jsx:109`); Tailwind `rose-600/700` (≈`#E11D48`/`#BE123C`,
e.g. `TradeHistoryTable.jsx:25`, `CloseDialog.jsx:228`,
`AccountAnalysis.jsx:168,182`); landing's own `--rose` `#B4485C`/`#E68094`
(`landing/public/assets/site.css:20,42`); the PDF's hardcoded `rgb(180, 72,
92)` (`ExportPdfButton.jsx:100`, also driving the header text color at
`:111` on paper exports) — which is landing's `--rose`, not the app's
`rose-600` and not `dm-negative`; shadcn `--destructive` `hsl(0 84.2%
60.2%)` ≈ `#EF4444` (`src/index.css:23`, used at `Login.jsx:51`). Same
pattern on warning: `dm-warning` `#854F0B` defined, used nowhere; real
warnings use Tailwind `amber-*`.
**Fix:** collapse to the `dm` scale everywhere per brand.md's own open
proposal — swap `rose-*`/`amber-*` loss/risk/warning usage for
`dm-negative`/`dm-warning` across the app, the landing site, and the PDF
banner/header color.

**4. Green is both the semantic "gain" color and a decorative UI color, on
the same screens and now on the landing homepage too.**
Surfaces: app-wide (P/L cells, primary buttons, progress bar, status dots,
chips), landing homepage.
Exact instances: `TradeHistoryTable.jsx:25` semantic emerald P/L vs.
`Screener.jsx:124` decorative emerald progress bar vs.
`AccountSection.jsx:126` decorative "connected" dot vs.
`ScanPresets.jsx:99` decorative preset chip vs. `CloseDialog.jsx:228`
(semantic) and `:343` (decorative "reset" button) four pixels apart — all
still present, unchanged from W36. New this cycle:
`landing/public/assets/site.css:381` (`.brokertag`) uses `--mint` for the
"Live now" badge on the Alpaca broker card on the homepage — a
connection-status label, not a P/L figure, styled in the same green that
means "gain" three sections down the same page (`.row4 .v.up`, `.mini
.pl.up`, `.tile .tv.up`, all also `--mint`). Landing's `--brand` (matches
`dm-accent`) is correctly used for primary CTAs, so this is a narrower
defect than the app's, but it's the same category of mistake, on the
highest-traffic page.
**Fix:** reserve mint/emerald for P/L and true connection-state truth only;
the Alpaca "Live now" badge and the app's decorative buttons/progress/chips
move to `dm-accent` or a neutral.

**5. The Analysis feature still carries two names in the one action that
leaves the product.**
Surfaces: the Analysis page, its exported PDF (forwarded to
accountants/spouses, outside app control).
Exact text: on-screen H1 `"Analysis"` (`AccountAnalysis.jsx:134`, correct)
but the same click passes `title={... "Performance Analysis"}` to the PDF
(`AccountAnalysis.jsx:157`) — the exact synonym brand.md's table (line 54)
forbids — and the PDF footer, present both on-screen
(`AccountAnalysis.jsx:202`) and in the exported file
(`ExportPdfButton.jsx:126`), reads `"DeltaMint — economic performance
report. Not a tax document and not investment advice."` Fully unaddressed
since W36; the filed fix was never applied.
**Fix:** change `AccountAnalysis.jsx:157` title prop to `` `${name} —
Analysis` `` and both "economic performance report" strings to "Analysis."
**Hand-off (unchanged from last cycle):** whether "economic performance
report" was a deliberate disclosure choice, not an accident, is
desk-editor's/compliance-gate's call before the replacement wording ships.

## Proposed rules for `brand.md` (silent today; vp-product to accept)

Carried forward from W36, still unaccepted (brand.md unchanged, confirmed
by reading it this cycle):

- *"No emoji anywhere in product surfaces, including transactional email;
  severity is conveyed by the `dm` semantic colors and words
  (critical/warning/info), not by color-coded emoji."*
- *"Lifecycle/status chips (closed, assigned, exercised, etc.) use a single
  neutral chip style with text, not a rainbow of Tailwind hues — reserve
  color for money and risk only."*
- *"Any surface that defines its own color tokens (landing, email, PDF)
  derives them from the `dm` hexes, not from Tailwind defaults or invented
  values."*
- Resolves brand.md's own open question (line 28-31): red/green are
  semantic only; the app's Tailwind emerald/rose/amber/sky/violet usage
  does **not** get sanctioned as-is.

New this cycle:

- *"'Screener' is the feature name with no modifier — never 'Market
  Screener,' never 'scanner.'"* brand.md's table already says "Screener";
  this makes explicit that "Market Screener" (used consistently across the
  app H1, the landing mockup, twice) is itself a violation, not a sanctioned
  longer form, so nobody "fixes" scanner→Market Screener and calls it done.
- *"A connection/session-state badge (e.g. 'Live now,' 'connected,'
  'streaming') never reuses the P/L gain color; it gets a neutral or
  `dm-accent` treatment."* Closes the landing `.brokertag` instance and
  generalizes the existing app-side decorative-green finding so it also
  covers the marketing site, not just `src/`.
