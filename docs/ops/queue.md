## Open

- [open] 2026-09-03 · head-of-trading · `spreadPairing.pairSide` (`supabase/functions/_shared/spreadPairing.ts` lines 77-124), and the structurally identical `nearestLong` loop in `supabase/functions/_shared/tradeReconstruction.ts` (lines 553-576, 691-700), assign each short leg the nearest *available* protective long by processing shorts in whatever order the input array happens to hold — not a true nearest/optimal assignment. When two untraceable short legs are each other's nearest-eligible long (e.g. puts short at 100 and 98, longs at 97 and 90 — both shorts prefer 97), which short gets the tight pairing depends entirely on array order, which for `spreadPairing.ts` is the order Alpaca's `GET /v2/positions` happens to return (not a documented, stable ordering) and for `tradeReconstruction.ts` is however `closedLots` was assembled. Reproduced by execution (`node --experimental-strip-types`, two orderings of the same four legs): one order pairs 100short/97long (3-wide) + 98short/90long (8-wide); the other pairs 98short/97long (1-wide) + 100short/90long (**10-wide**) — the exact "10-wide spread invented, max loss doubled" pattern named in `.claude/agents/head-of-trading.md` as a defect this product has already shipped once. Only affects legs pairing could not trace to a filled multi-leg order (legged-in entries, partial closes, pre-order-history syncs) — traceable multi-leg orders are unaffected. Fix: give `pairSide`/`nearestLong` a deterministic, order-independent assignment (e.g. process shorts sorted by strike, or run a true minimum-total-width/stable matching over all competing shorts before mutating any leg's qty) so the same live position set always reports the same width and max risk regardless of API/array order. systems-engineer to confirm the fix and re-run `spreadPairing.test.ts`/`tradeReconstruction.test.ts`.
- [open] 2026-09-03 · head-of-trading · `syncAccounts/index.ts` computes a real, finite `maxRisk` for every 2-leg `call_spread`/`put_spread` (line 300: `(spreadWidth - netCredit) * qty * 100`) even when the row is later flagged `adjusted: true` (a corporate-action-adjusted OCC contract, e.g. `AAPL1`, that no longer delivers 100 shares at the strike). Fix: in `syncAccounts/index.ts`, either set `maxRisk: null` on an `adjusted` flat-spread row before it reaches `totalRisk`, or make `totalRisk`/the `flat` reducer treat `r.adjusted` the same as a null risk (excluded from the sum, `complete: false`, ticker added to `undefinedRisk`). systems-engineer to confirm and add a syncAccounts-level regression (no test file currently covers this function's totals reducer).
