# Trading audit — 2026-W36 (Thursday, 2026-09-03)

head-of-trading · standing audit of the market-facing path, against `main` at
`58a1a1b` (staging carries only ops/content/docs commits ahead of `main` this
week — nothing on the trading path — so this audit covers the branch that
matters).

## Verdict: FINDINGS

Two new, reproducible defects on the risk-arithmetic path — neither proven to
be misrepresenting a number on a *currently open* production position (I have
no production account read access; see "What I did not examine"), but both
are live in `main`'s code today and will silently misstate a max-risk figure
the moment the triggering shape occurs. Both are the same defect class this
product has shipped and fixed once before, now reachable through a different
door than last time. No STOP: I found nothing that is *known*, right now, to
be wrong on the screen of a real account.

## Findings

### 1. Spread pairing is order-dependent when two untraceable shorts compete for the same nearest long — EXECUTED

**File:** `supabase/functions/_shared/spreadPairing.ts`, `pairSide` (lines
77–124). Same shape in `supabase/functions/_shared/tradeReconstruction.ts`,
`nearestLong` (553–576) as used by `buildTrades` (691–700) — read-derived,
not separately executed.

`pairSide` was rewritten (per its own comment) to fix "legs paired to the
first long found instead of the nearest protective one." It now gives each
short the nearest *available* long — but it still processes shorts in
whatever order the input array holds, mutating each long's remaining qty as
it goes. When two shorts are *each other's* nearest eligible long, whichever
short is processed first wins the tight pairing, and the other is pushed onto
whatever is left — which can be far wider than either short's true nearest
long.

**Failing case (executed, `node --experimental-strip-types`):** shorts at
$100 and $98 strike, longs at $97 and $90 (all same ticker/expiry, puts). The
100-short's nearest long is 97 (distance 3); the 98-short's nearest long is
*also* 97 (distance 1) — closer for the 98-short than for the 100-short.

```
positions=[100short, 98short, 97long, 90long]  → 100s/97L (3-wide), 98s/90L (8-wide)
positions=[98short, 100short, 97long, 90long]  → 98s/97L (1-wide),  100s/90L (10-wide)
```

Same four live legs, same account, no trade placed in between — the reported
width and max risk for the 100-strike short swings from a 3-wide spread to a
**10-wide spread** (more than 3x the max-risk dollar figure) purely because
of array order. `spreadPairing.ts`'s order comes from Alpaca's
`GET /v2/positions` response, whose ordering is not a documented, stable
contract; `tradeReconstruction.ts`'s comes from however `closedLots` was
assembled from the activity feed. This is precisely the "a 10-wide spread
invented, max loss doubled" failure `head-of-trading.md` names as a defect
this product has already shipped once — reproduced here through the *loose*
(untraceable-to-an-order) pairing path rather than the first-match path that
was fixed.

**Reach:** only legs pairing cannot trace to a filled multi-leg order —
legged-in entries, partial closes leaving a remainder leg, or an account
whose order history predates the order-provenance sweep. Legs claimed by
`claimOrderLegs` (traceable multi-leg orders) are unaffected and correctly
order-independent.

**Dollar consequence:** computable per the case above — the 100-strike
short's displayed max risk moves between roughly `(3 − credit) × 100` and
`(10 − credit) × 100`, a swing on the order of $700 per contract for this
example, with no code change and no market move.

**Hand-off:** systems-engineer to fix (deterministic assignment — sort
shorts by strike before pairing, or a true minimum-total-width/stable match
across all competing shorts in one pass — before touching any leg's qty),
and to judge whether `tradeReconstruction.ts`'s identical shape has ever
produced a misattributed realized P/L on a closed spread; if it has,
that is a closed-result question for **investment-analyst**, not mine.

### 2. An adjusted contract's fabricated max risk reaches the account total, though the per-row screen was fixed — EXECUTED

**File:** `supabase/functions/syncAccounts/index.ts` (lines 295–300,
368–369, 416–436), `supabase/functions/_shared/positionKinds.ts`
(`totalRisk`, lines 213–226).

`syncAccounts` correctly re-derives `adjusted` per row from the leg symbols
(line 259 for singles, line 341/368 for multi-leg) and the frontend correctly
withholds Width/Break-Even/Max Risk on an adjusted row (`SpreadTable.jsx`
132–155, `positionKind.js` line 26). But the backend computes `maxRisk` for
every flat 2-leg spread *unconditionally*, before that flag is even attached
(`const maxRisk = (spreadWidth - netCredit) * s.qty * 100` at line 300, run
for every `call_spread`/`put_spread` row regardless of `adjusted`), and never
excludes an `adjusted` row from the sum that becomes the account total.
`totalRisk` (the shared reducer used for the total) only excludes a row when
`maxRisk` is `null`/non-finite — it has no knowledge of `.adjusted` at all.

**Executed:**

```
row = { type: "put_spread", adjusted: true, maxRisk: 183 }
totalRisk([row]) → { risk: 183, complete: true, undefinedRisk: [] }
```

`complete: true` means no floor ("+") is shown — the fabricated figure enters
`account.totals.risk` and `account.riskPct` and is displayed on
`AccountSummaryCard.jsx` ("Max risk") and `AccountSection.jsx` ("Risk /
Equity") as a confident, complete number, exactly as if the contract's width
were real.

This is the "risk computed from a width an adjusted contract no longer
delivers" defect `head-of-trading.md` names as already shipped once — the
per-position display was fixed (correctly withholds), but the *total* was
not, because the total is computed from the same unfiltered `maxRisk` before
`adjusted` gets checked anywhere in the reducer.

**Dollar consequence, worked:** a 1-lot adjusted put spread, strikes $60/$56.67
(a pre-split $90/$85 5-wide re-struck 3-for-2), $1.50 net credit. Reported
account-total contribution: `(3.33 − 1.50) × 100 = $183`. If the adjusted
contract in fact delivers 150 shares (the split's real ratio), the true worst
case is `(3.33 − 1.50) × 150 = $275` — the account total silently
understates this position's contribution by **~33%**, with the "Risk /
Equity" chip showing a plain percentage rather than the floor indicator that
exists for exactly this situation.

**Reach:** any account holding a 2-leg vertical spread where both legs are on
an adjusted OCC root — realistic on any account with a position that
predates a split/spin-off/special dividend on the underlying. Single-leg
adjusted rows and iron condors were not checked for the same gap (see below).

**Hand-off:** systems-engineer to fix — either null out `maxRisk` on an
`adjusted` flat-spread row before `totalRisk` sees it, or teach the `flat`
reducer to treat `r.adjusted` as undefined risk (excluded from the sum,
`complete: false`, ticker listed in `undefinedRisk`). No test currently
covers `syncAccounts`'s totals reducer at all (it isn't a `_shared/` pure
function); worth extracting the totals math to something testable while
this is touched.

## Reviewed and clear (executed or read-confirmed, no new finding)

- **`npm test`: 189/189 pass**, no regressions on `main` at `58a1a1b`.
- **Nearest-long pairing, the traceable path** (`claimOrderLegs` +
  `pairSide` within one filled multi-leg order): order-independent, correct.
  Only the untraceable/"loose" path has Finding 1's defect.
- **Partial share coverage on a multi-contract short-call leg**
  (`classifyLeg`): confirmed intentional and tested
  (`positionKinds.test.ts` "a partially covered holding reports as naked") —
  reports the *whole* leg naked rather than splitting covered/naked
  fractions, which is the conservative direction (more "Unlimited," never
  less). Not a finding.
- **`price_untrusted` / moneyness on a missing quote**: still returns `null`
  moneyness rather than defaulting to "OTM" everywhere I checked
  (`syncAccounts.ts` 258, 364; `marketPrice.spotFromSnapshot`/
  `closingSpotFromSnapshot`). `getSpot`/`getSpots` unchanged since the JPM
  incident postmortem; trade-vs-quote divergence check intact
  (`MAX_SOURCE_DIVERGENCE_PCT`).
- **Naked-call watch rule** (`watchRules.nakedShortCalls`): re-read against
  its own tests — per-contract partial coverage by shares *and* by a
  protective long, nearest-expiry-first, correctly excludes call-spread and
  iron-condor shorts. All 11 of its tests pass, including the pinned
  production incident ("six call spreads on one account, six false
  criticals"). Note: this rule computes uncovered contracts *per contract*
  (more precise than the dashboard's whole-leg `classifyLeg`), which is the
  right direction for an alert but means the watch's contract count and the
  dashboard's naked/covered label can differ for the same leg — not a
  safety defect (the dashboard is the more conservative of the two), flagging
  for awareness only.
- **CSP collateral check on Alpaca**: no client-side `cash ≥ strike×100`
  test, by design — confirmed the design note in `positionKinds.ts` and
  `openPosition/index.ts` (no such check on a single-leg short put) match:
  Alpaca's own level-2 gate is the collateral check. Consistent, not a gap.
- **Wheel prefix / single-leg open path** (`openPosition/index.ts`
  118–146): covered-call collateral refused client-side before the order is
  sent (`heldShares` check); CSP relies on the broker per above.
  `wheel_client_prefix` used for every single-leg order, matching the
  file's own stated invariant that a single-leg order from this app is
  always a wheel half.
- **`closeSpread`/`manageOrder`**: single-leg closes correctly routed through
  the explicit-legs path (verified `useCloseOrder.js`'s `wholeParams` never
  sends a null-leg multi-leg body for a single position);
  `recordAttempt`/`updateAttempt` called on every branch of `closeSpread`
  and `manageOrder`'s replace path (the existing escalated ticket that
  `openPosition` doesn't call `recordAttempt` on the open side is
  unchanged this week — still open, not re-raised).
- **The max-loss invariant and its bought-back exemption**
  (`tradeReconstruction.ts` 1024–1060): present, tests pass, exemption
  (`close_reason === "closed"`) confirmed scoped to rows the strikes did not
  close, matching the ARKK postmortem in its own comment.
- **`refuseMassDelete` / snapshot-before-write**: confirmed wired as the
  only gate on `tradeHistory/index.ts`'s write path (line 289–292), snapshot
  taken and the refusal checked before any write (287–322); `lotFromOption`
  used identically here and in the reconstruction's own filter, per the
  comment's stated invariant.

## What I did not examine

- **No production account data.** Everything above is code-level (unit
  fixtures via `node --experimental-strip-types`, or read-derived from the
  source and its tests). I have no way to confirm whether any currently-open
  position on a real account actually has an untraceable competing-shorts
  shape (Finding 1) or an adjusted-contract flat spread (Finding 2) *right
  now* — which is why the verdict is FINDINGS, not STOP.
- **Whether `BREVO_API_KEY` is set in production** — I could not confirm
  from the repo or `docs/ops/` whether `positionWatch`'s emails
  (session alerts, daily report) are currently a no-op or actually being
  sent. Doesn't change either finding above, which are dashboard/total
  issues, not watch/email issues.
- **`iron_condor` and single-leg rows for the same adjusted-contract total
  gap as Finding 2.** I checked and confirmed the flat 2-leg case
  concretely; I did not fully trace whether `condorByTicker` (line 417–420,
  summed via `putSideRisk`/`callSideRisk` computed the same unconditional
  way at lines 371–372) or `stockLike`/`stressLossOfKind` totals have the
  same gap. Worth systems-engineer's five minutes given how the flat case
  turned out.
- **A possible duplicate/unresolved-row accumulation in the `alerts` table**
  for a standing condition that persists across trading days (`dedupe_key`
  in `positionWatch/index.ts`'s `reconcile()` is day-scoped, and I could not
  fully convince myself the resolution logic collapses a still-true
  condition's prior-day row). I traced this as far as static reading gets
  me and could not execute it against a real database to confirm either
  way. I'm not reporting it as a finding — I don't have enough confidence in
  either direction — but flagging it as a specific question for
  systems-engineer: does a standing critical condition (e.g. a naked call
  open for a week) produce one open `alerts` row or several, and does that
  change what the daily report shows? The report itself (`openAlerts` query,
  `positionWatch/index.ts` 260–266) filters on `first_seen_at`, which only
  reads correctly if a fresh row really is written each day for a
  persisting condition — I could not verify that without a live database.
- **Orders/manageOrder replace-price arithmetic** (`orderReplace.ts`,
  `closeWalk.js`'s `nextLimit`) — read the files, did not independently
  re-derive the walk's stepping math against a live quote ladder.
- **Options-buying-power and margin figures** (`optionsBuyingPower` on the
  account object) — passed through from Alpaca unchanged; not something
  this app computes, so out of my territory, noted rather than audited.
