## Findings

### 1. The entry path treats shares already backing a short call as free cover — a "covered call" the screen prices as bounded is naked the moment it fills — EXECUTED · BLOCKING

**Files:** `supabase/functions/_shared/heldShares.ts:51`,
`supabase/functions/_shared/optionScan.ts` (`buildSingle`, `covered_call`
branch), `supabase/functions/_shared/orderWarnings.ts` (`coverWarning`),
`supabase/functions/openPosition/index.ts:86–95`,
`supabase/functions/scanEntries/index.ts:43`,
`supabase/functions/findEntry/index.ts:28`.

`heldShares` returns the broker's raw share count. Nothing on the entry path
reduces it by contracts already written against it. `allocateCallCover` — the
one allocator the dashboard *and* the watch read, written on 8 Sep precisely
because two copies of this arithmetic disagreed — does reduce it, and is
never consulted before an order.

**Failing case (executed):** account holds 100 TSLA, already short 1×
TSLA 261016C450.

```
allocateCallCover([short 450C], {TSLA:100}) -> fromShares:1, covered:1, uncovered:0
                                sharesLeft  -> {"TSLA": 0}          <- nothing free
openPosition coverWarning("Wheel","TSLA", held=100, contracts=1) -> null   <- no warning
optionScan buildSingle(covered_call, shares=100)
   -> ok=true  maxContracts=1  maxRisk=$29,400  collateral=$30,000
after the fill, allocateCallCover on both shorts:
   TSLA261016C00450000 -> covered:1 uncovered:0
   TSLA261120C00460000 -> covered:0 uncovered:1      <- naked
```

The screener ranks it, the ticket prints `Max risk $29,400`, `openPosition`
raises no warning, and the first thing that tells the truth is the dashboard
("Naked call · Unlimited") and the watch's `naked_short_call` critical —
after the money is committed.

**Dollar consequence:** the $29,400 figure is a bound the position does not
have. TSLA at 420, short the 460C for $6.00: at 600 the uncovered contract
has lost $(600−460−6)×100 = **$13,400 and rising without limit**, against a
screen that said $29,400 was the worst case.

Two sub-defects, same root: `coverWarning` counts **shares alone** — the
exact arithmetic `callCover.ts`'s own header says was removed on 8 Sep for
calling a defined-risk spread naked, now a third live copy, and it also
false-alarms a poor-man's covered call as uncovered. `buildSingle`'s
`maxContracts: Math.floor(held / 100)` has the same blindness.

**Hand-off:** systems-engineer — both `heldShares` callers should pass live
option legs through `allocateCallCover` and expose *free* cover;
`coverWarning` should take an allocation, not a share count.

### 2. A short stock lot carries a finite max loss, and the account risk total prices it as if it were long — EXECUTED · BLOCKING

**Files:** `supabase/functions/_shared/positionKinds.ts` — `stressPL` case
`SHARES` (line 170, `Math.abs`), `stressLossOfKind` case `SHARES` (line 121),
`riskOfKind` case `SHARES` (252–255); reached via
`_shared/spreadPairing.ts`'s `toSharePosition` and `syncAccounts/index.ts`'s
`singleRow`.

`Math.abs` discards the sign of the holding, so a short lot is scored as a
long lot.

**Failing case (executed):** short 100 TSLA, basis $400, spot $420.

```
row.maxRisk               = $40,000   <- finite, on a position unbounded to the upside
stressPL at +15% ($483)   = +$6,300   (should be -$6,300)
stressPL at -15% ($357)   = -$6,300   (should be +$6,300)
```

Magnitude survives in isolation by accident (the total takes the worse of
two shocks). It does not survive netting — short 100 TSLA @420 plus short 1×
TSLA 400P @$8 (the post-assignment "reverse wheel" shape):

```
reported: {"risk": 9800, "complete": true}
true:     P/L at +15% = -$5,500; at -15% = +$2,800 -> true risk $5,500
```

**$9,800 reported against a true $5,500 — a 78% overstatement, presented as
complete, no floor indicator.** Flip the second leg to a short call and it
understates instead. This is not exotic: early assignment of a short call on
a margin account leaves the account short 100 shares, and the product
already anticipates short lots elsewhere (`spreadLegs`'s `buy_to_close`
branch, `toSharePosition`'s own `Math.abs`). The $40,000 flows into
`totals.notional` as a complete number labelled "Max loss (stock to 0)",
meaningless for a short. `positionWatch` never sees it either — Finding 7.

**Hand-off:** systems-engineer — `stressPL`/`stressLossOfKind` must carry the
sign; `riskOfKind(SHARES)` must return `null` for negative `shareQty`
(unbounded, the posture `NAKED_CALL` already takes); `labelOfKind`/
`riskLabel` need a short-stock case.

### 3. `moneyness` is a coloured verdict rendered off an untrusted spot — `spotTrusted` is computed, shipped to the browser, and never read by either dashboard renderer — EXECUTED (price) / read-derived (render)

**Files:** `supabase/functions/syncAccounts/index.ts:297,472`
(`moneyness: !(stockPrice > 0) ? null : itm ? "ITM" : "OTM"`),
`src/lib/positionKind.js` (`moneynessTone`/`moneynessCell`),
`src/components/dashboard/PositionCard.jsx:132`,
`src/components/dashboard/SpreadTable.jsx:181,191`.

The only gate is `stockPrice > 0`. `spots[ticker].trusted` is read into the
row as `spotTrusted` and then nothing on the dashboard reads it — not the
chip, not the tone, not the price cell. `src/pages/OptionChain.jsx:259` does
check it, which is what the rest of the dashboard should look like.

**Failing case (executed), the JPM shape from `marketPrice.ts`'s own header:**

```
spotFromSnapshot({trade 354.33, quote mid 363.54}) ->
  {"price":354.33,"source":"trade","trusted":false,
   "reason":"Last trade $354.33 and quote mid $363.54 disagree by 2.6%."}
syncAccounts renders moneyness = "ITM"   (spotTrusted=false, nothing on screen says so)
```

The harmful branch is the `dailyBar` fallback (`marketPrice.ts:95–98`): no
trade, no usable quote — a halted or barely-traded name mid-session — returns
a bar that may be a day old, `trusted:false`, and the card paints a confident
green **OTM** chip from it. The named historical defect ("a green chip on a
position sitting through its strike") arriving through a different door: not
a missing quote, an *untrusted* one. `AGENTS.md`'s own rule — "Never return a
number without its provenance … and the UI shows it" — the server keeps its
half; the dashboard does not.

**Hand-off:** systems-engineer — withhold the verdict when `!spotTrusted`
(slate chip, as `moneynessCell` already does for null), or render an explicit
untrusted marker on the price cell.

### 4. `allocateCallCover` takes the *first* eligible long, not the nearest — a covered call's max risk swings $500 ↔ $9,500 on broker list order alone — EXECUTED, same class as W36 #1, new file

**File:** `supabase/functions/_shared/callCover.ts:78–117`. `longPool` is
built in array order and consumed first-fit. Strike does not matter for
*whether* a short is covered, but `riskOfKind(COVERED_CALL)` reads
`cover.byLongs[].strike` to bound the row (`positionKinds.ts:225–232`), so
the *choice* of long sets the dollar figure.

**Failing case (executed end-to-end through `pairSpreads`):** short NVDA
261016C150; longs NVDA 270115C160 and NVDA 270115C250 (different expiry, so
neither pairs as a vertical); credit $5.00.

```
broker lists [short, 250L, 160L] -> covered by 250 -> maxRisk = $9,500
broker lists [short, 160L, 250L] -> covered by 160 -> maxRisk =   $500
```

Same four live legs, same account, no trade in between — a **$9,000 swing**
in the Detailed table's risk cell and in `totals.notional`, decided by the
ordering of `GET /v2/positions`, which Alpaca does not document as stable.
The "first long found instead of the nearest protective one" pattern,
reproduced inside the module written on 8 Sep to be the single source of
truth.

**Hand-off:** systems-engineer — same fix shape as W36 #1: sort the long pool
deterministically (nearest protective strike, then expiry, then symbol)
before consuming, in `callCover.ts` and in `spreadPairing.pairSide`'s short
ordering together, so the two cannot diverge again. **Fix together with
Finding 13** — same defect, two files.

### 5. A poor-man's covered call reads "Covered call", break-even −$12.00, "Max loss (stock to 0)" on an account holding no stock — EXECUTED

**Files:** `supabase/functions/_shared/spreadPairing.ts` `coverExtra:617`
(`shareBasis: lot ? … : 0`), `_shared/positionKinds.ts`
`breakEvenOfKind` case `COVERED_CALL:272` (`shareBasis − credit`),
`src/lib/positionKind.js` (`isStockRisk`/`riskLabel`),
`src/components/dashboard/PositionCard.jsx:17–31,45`.

**Failing case (executed):** long TSLA 270115C250 @ $180.00, short TSLA
261016C400 @ $12.00, no shares.

```
covered_call  maxRisk=0  breakEven=-12  collateral=0  shareBasis=0  basisSource="broker"
long_option   maxRisk=18000  breakEven=430
```

Badge **CC**, footer `Break-Even −$12.00`, `Capital tied up $0.00`, "Max loss
(stock to 0)", tooltip "Broker basis — premiums could not be linked to these
shares". The PMCC's real break-even is roughly long strike + net debit ≈
**$418**. `−$12.00` isn't a number about this position — it's `0 − credit`,
where the `0` is a missing share lot. `maxRisk = 0` is correctly reasoned
(the long's premium sits on the long's own row); the break-even, label and
basis note are covered-call vocabulary misapplied to a diagonal.

**Hand-off:** systems-engineer — `breakEvenOfKind(COVERED_CALL)` should
return `null` when cover came from `coverLongs` rather than a share lot, and
that row needs a label that isn't "stock to 0".

### 6. An unbalanced iron condor closes 1:1 — `syncAccounts` stamps `longRatio/shortRatio: 1` on every non-ratio row, shadowing `putRatio` — EXECUTED

**Files:** `supabase/functions/syncAccounts/index.ts:481–482`,
`src/lib/spreadLegs.js:112–123` (`ratio: spread.shortRatio || putRatio`).

```
row: iron_condor, putRatio 2, callRatio 1, plus syncAccounts' longRatio:1/shortRatio:1
  legs sent:  P5000 ratio 1 buy · P4950 ratio 1 sell · C6000 ratio 1 buy · C6050 ratio 1 sell
same row WITHOUT the syncAccounts stamp:
  legs sent:  P5000 ratio 2 buy · P4950 ratio 2 sell · C6000 ratio 1 buy · C6050 ratio 1 sell
```

`spreadLegs`'s own header says routing is derived, not listed, precisely so a
structure cannot be mis-sent — and it is, because the *ratio* is read from a
field `syncAccounts` overwrites. The close ticket quotes and sends a balanced
condor: the user closes a 2:1 condor and **one put spread per unit stays
open**, after a ticket that priced and confirmed the whole structure. On a
50-wide SPX put spread that is up to $5,000 of residual risk per unit
believed flat; on a 5-wide equity condor, $500.

**Reach:** only a single multi-leg order that opened unequal sides — hand-
built or opened outside the app on a connected account. Not producible by
the scanner. Rare, but exactly a "what the order sends vs what the screen
said" defect.

**Hand-off:** systems-engineer — `spreadLegs` should not fall back through
`shortRatio` for a condor, or `syncAccounts` should stop stamping
`longRatio/shortRatio` on rows that are not ratios.

### 7. The watch never sees a share position at all — `position_oversized` cannot fire on stock, and short stock is unwatched — read-derived (call site) / EXECUTED (`sharesByTicker`)

**Files:** `supabase/functions/positionWatch/index.ts:46,277`
(`positions.filter(p => parseOCCSymbol(p.symbol))`),
`supabase/functions/_shared/watchRules.ts:21`
(`sharesByTicker`, `if (!(qty > 0)) continue`).

Every rule in `evaluate` runs inside a loop over option legs only. Shares
enter solely as a *cover count*, and short shares are dropped there too:

```
sharesByTicker([{symbol:"TSLA", qty:"-100"}]) -> {}
```

So `position_oversized` — documented in `alert-rules.md` as firing on "one
position's market value" using the broker's own `market_value` specifically
so it holds when our pricing is suspect — **cannot fire on a stock
holding**: a single name at 60% of equity is silent. And a **short** stock
lot (Finding 2's shape, unbounded to the upside) is watched by nothing —
`alert-rules.md`'s opening claim that "a naked short is the single most
important thing to alert on" is true only for calls.

**Hand-off:** systems-engineer for the code; the rule text is head-of-
trading's to revise once the code direction is settled.

### 8. On a market holiday or a half-day the session watch takes the live-ladder branch, and the code comment asserts the opposite — EXECUTED

**Files:** `supabase/functions/_shared/watchRules.ts:114–123`,
`supabase/functions/positionWatch/index.ts:289–292`.

`watchRules.ts` states: "Holidays are not modelled — on a holiday this
returns 'open' and the closing price is used anyway, because getClosingSpots
is what a shut market wants." The code does the reverse:

```
sessionPhase(2026-11-26T15:00Z, Thanksgiving) = "open"; judgeOnLivePrices = true
positionWatch:291 -> mode==="daily" || !live  is FALSE -> getSpots (live ladder)
sessionPhase(2026-11-27T19:00Z, 1h past the 1pm ET half-day close) = "open"
```

With nothing trading, the 30-minute ladder marks every price untrusted, so
every ticker raises `price_untrusted` and **`short_through_strike` /
`short_near_strike` are never reached** — the precise failure the
`sessionPhase` work was written to cure, still live on the ~9 full holidays
and ~3 half-days a year. The holiday miss is benign (nothing moves); the
half-day afternoon is not. `reconcile`'s `PRICE_DEPENDENT` guard correctly
keeps existing criticals open throughout — that half is intact.

**Hand-off:** systems-engineer — a holiday/half-day calendar, or invert the
branch so an untrusted live ladder falls back to the close rather than
suppressing every price-dependent rule.

### 9. A partly-covered ratio is badged "Stock repair" and prints "—", and the fields computed to say otherwise are dropped before the screen — EXECUTED (pairing) / read-derived (UI)

**File:** `supabase/functions/_shared/spreadPairing.ts` `tagStructures:725`

trader to work out which cover was claimed" — computed and thrown away.

**Hand-off:** systems-engineer to render them; the wording is head-of-

### 10. `syncAccounts` substitutes a break-even that `positionKinds` deliberately withheld on an adjusted contract — latent, currently caught by the UI — EXECUTED

**File:** `supabase/functions/syncAccounts/index.ts:304`
(`breakEven: s.breakEven ?? (isCall ? leg.strike + leg.entryPrice : leg.strike - leg.entryPrice)`).

`breakEvenOfKind(SHORT_CALL_UNJUDGED)` returns `null` on purpose ("the
deliverable is what a corporate action changed"). `??` fires on exactly that
null and fills it with strike-plus-premium arithmetic about a deliverable the
contract does not have:

```
short 1× AAPL1 261016C150 @ $3.25
  positionKinds.breakEvenOfKind -> null
  syncAccounts renders          -> 153.25
```

Both `PositionCard` and `SpreadTable` currently print "—" because they
branch on `s.adjusted` first, so nothing reaches a user today. But the
fabricated number is on the API payload, one un-guarded consumer away — a
convenience default in a file whose neighbouring comments are entirely about
not doing this. A new default where "I don't know" belonged: a ticket, at low
severity given today's UI guard.

**Hand-off:** duty-engineer — a one-line fix (`s.breakEven !== undefined ?
s.breakEven : …`, or drop the fallback for kinds that withhold).

### 11. The moneyness chip is frozen at sync time while the streamed price beside it moves — read-derived

**Files:** `src/components/dashboard/AccountSection.jsx:99`,
`src/components/dashboard/StrikeLadder.jsx:161`,
`src/components/dashboard/PositionCard.jsx:132`.

The stream overlay rewrites `stockPrice` and sets `spotTrusted: true`, but
does not recompute `moneyness`, which is a server field. `StrikeLadder` draws
its marker from the overlaid `stockPrice`; the chip above it carries the
verdict from the last completed sync. `useLiveSync` re-syncs continuously
(≈1s idle + round-trip normally), widening to **5–60s under rate-limit
backoff**, and **unbounded while a refresh is failing** — exactly the state
`StaleDataNotice` shows while the stream keeps the price moving underneath a
frozen chip. Visible symptom: a marker inside the max-loss wing beside a
green, OTM chip.

**Hand-off:** systems-engineer — recompute moneyness client-side from the
same `stockPrice` the ladder uses, or blank the chip when
`spotSource === "stream"`.
