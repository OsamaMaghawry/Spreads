## Findings

### 1. `SpreadTable`'s own footer total disagrees with the account's "Max risk" tile for a short call covered by a long call struck below it — EXECUTED

**Files:** `src/components/dashboard/SpreadTable.jsx` (lines 31–44, the
table's local `totals` reduce), `supabase/functions/_shared/positionKinds.ts`
(`riskOfKind`'s `COVERED_CALL` branch, lines 216–233), `syncAccounts/index.ts`
(`totals.risk`, line 567, via `stressTotal`).

A short call covered by a *long call* rather than shares (Alpaca's
poor-man's-covered-call shape — the exact `352.50 long / 375 short` example
`callCover.ts`'s own comment uses for "still a spread") reaches the dashboard
as **two independent rows**: a `covered_call` row for the short and a
`long_option` row for the long, produced by `spreadPairing.ts`'s leftover
pass whenever the two legs cannot be traced to one order (the common case —
a PMCC is normally built in two separate trades). `riskOfKind`'s comment for
this case states the design intent explicitly: *"the two rows add up to the
pair's real bound... where the long sits BELOW the short this comes out at
nothing... the cost is on the long's row."* That is true of the **backend
account total**, which does not sum the rows' `.maxRisk` fields — it reprices
the whole ticker's book at a shocked spot via `stressTotal`/`stressPL`, which
nets the short's collected premium against the long's cost correctly. It is
**not** true of `SpreadTable.jsx`'s own "Total" row at the bottom of the
Detailed positions table, which sums `.maxRisk` per row directly (line 36:
`maxRisk: a.maxRisk + (bounded ? s.maxRisk : 0)`) — exactly the naive
addition the code comment describes as correct and the backend deliberately
does *not* do.

**Executed (`node --experimental-strip-types`, via `pairSpreads` — the live
pairing function — then `stressTotal`, the live account-total function):**

```
positions: long TSLA 352.50C @13.57, short TSLA 375C @2.26 (no shares held)
pairSpreads() output:
  covered_call  maxRisk 0     breakEven -2.26   (Finding 2, below)
  long_option   maxRisk 1357  breakEven 366.07

SpreadTable.jsx footer ("Total" row, naive sum of .maxRisk):        $1,357
account.totals.risk via stressTotal (AccountSummaryCard "Max risk"
  tile, AccountSection "Risk / Equity"), spot $370:                 $1,131
discrepancy, same screen, same position, same sync:                   $226
```

$226 is exactly the short leg's collected premium ($2.26 × 100) — the amount
the row-split intentionally "gives" to the long's row and that the naive sum
never gets back. This is not a rounding artifact; it is structural, and it
scales with contract count and premium size. I checked the other direction
(long strike *above* the short — the ordinary bear-call-credit shape) and
confirmed the naive sum happens to be algebraically correct there — `(width
− short credit) + long premium = width − net credit` — which is exactly why
this has stayed hidden: the existing test
(`spreadPairing.test.ts` "a long call covers a short call whatever its
strike") only asserts `short.maxRisk !== null` and never checks the long
row or any total, so neither shape's total was ever verified against the
other.

**Dollar consequence:** the account's own headline "Max risk" tile is
correct; a trader who instead reads the Detailed table's own total — the
same number of clicks away, on the same screen — sees a figure $226 high on
this example, growing with size (a 10-lot version of the same trade is
$2,260 apart). Nothing here is unbounded or hidden; it is two confident,
disagreeing numbers on one screen, which is the specific failure mode
`head-of-trading.md` names ("an attribution that... published a loss beyond
a spread's arithmetic maximum, with the account total still reconciling").

**Reach:** any account holding a short call whose only cover is a long call
struck *below* it, where the two legs are not provably one order (built in
two trades, which is the common way to enter or roll a PMCC). Not reachable
through shares-covered calls, condors, or the credit-direction shape.

**Hand-off:** systems-engineer to fix — either make `SpreadTable.jsx`'s
footer read `account.totals.risk` directly instead of re-deriving it (it
already has `account` in scope one level up in `AccountSection.jsx`), or, if
a table-scoped subtotal is wanted for a filtered ticker view, teach it to
route stock-like rows through `stressTotal` the same way the backend does
rather than summing `.maxRisk`.

### 2. The same position's covered-call row shows a break-even of **−$2.26** — EXECUTED

**File:** `supabase/functions/_shared/positionKinds.ts`, `breakEvenOfKind`
(lines 264–286), `COVERED_CALL` case (line 271–272).

`breakEvenOfKind(COVERED_CALL, p)` always returns `(p.shareBasis || 0) −
credit`, with no branch for `p.coverLongs` — unlike `riskOfKind`, which
explicitly branches on `coverLongs` for this exact shape three lines away in
the same file. When the cover is a long call and no shares are held on the
ticker, `shareBasis` is never set (`spreadPairing.ts`'s `coverExtra` only
populates it from `shareLots[ticker]`, which does not exist here), so it
defaults to 0 and the function returns `0 − credit`.

**Executed, same fixture as Finding 1:** the `covered_call` row's `breakEven`
comes back **`-2.26`** — a stock price below zero, rendered by
`SpreadTable.jsx` (line 240, `fmtMoney(s.breakEven)`) as a plain dollar
figure with no caveat. The real break-even for this pair (long strike + net
debit) is $377.31; the screen shows a number that cannot exist for any
stock.

This is squarely the pattern `head-of-trading.md` names first: *"a figure
that cannot be trusted is withheld and shown as such — never substituted,
never defaulted."* `riskOfKind`'s own `COVERED_CALL` branch demonstrates the
fix is known and already written for the sibling function — `breakEvenOfKind`
was just never given the same branch.

**Dollar consequence:** not directly a dollar figure (break-even is a price,
not a loss), but it is the number a trader reads to decide whether a
position is "safe" relative to the current stock price — a negative number
is confusing rather than merely wrong, which is arguably worse than a
plausible-looking bad number for how quickly it would be noticed and
distrusted, or dismissed as a display glitch and ignored.

**Reach:** identical to Finding 1 — any long-call-covered short call with no
shares held on the name.

**Hand-off:** systems-engineer — give `breakEvenOfKind`'s `COVERED_CALL` case
the same `coverLongs` branch `riskOfKind` already has (break-even at the
long strike, shifted by the net debit/credit across both legs), and return
`null` rather than a shares-basis figure when `coverLongs` exist and no
shares back the position — the two are not one strategy and averaging their
formulas is what produced the negative number.
